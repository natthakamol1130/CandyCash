1. Stakeholder Problem, Chosen Context & Actors

ปัญหาของผู้ใช้งาน (Stakeholder Problem): เว็บหรือแอปจดบันทึกรายรับ-รายจ่ายทั่วไปมักมีแค่ฟอร์มกรอกข้อมูลธรรมดาที่ยอมให้คีย์รายจ่ายจนยอดเงินติดลบ เวลาจดผิดโฟลเดอร์ก็ต้องลบแล้วพิมพ์ใหม่ทั้งหมด เวลาเผลอกดลบรายการทิ้งก็กู้คืนไม่ได้ และไม่ช่วยคำนวณว่าจากงบที่เหลือในเดือนนี้ "วันนี้ยังใช้เงินได้อีกกี่บาท"

บริบทของระบบ (Chosen Context): CandyCash คือเว็บสมุดจดบันทึกรายรับ-รายจ่ายส่วนตัวอัจฉริยะ (ไม่ได้ผูกกับธนาคารจริง แต่ให้ผู้ใช้สร้างโฟลเดอร์จำลองเพื่อจดบันทึกและบริหารเงินด้วยตนเอง) ที่มีเกราะป้องกันยอดเงินติดลบ ระบบยืนยัน 2 ชั้น (Double-Check) เวลาจะยกเลิกหรือย้ายรายการข้ามโฟลเดอร์ ถังขยะสำหรับกู้คืนรายการที่ยกเลิก ตัวคำนวณงบใช้จ่ายรายวันอัตโนมัติ (Daily Safe-to-Spend) และมี ADMIN คอยอำนวยความสะดวกเรื่องหมวดหมู่กลางและสูตรจัดงบมาตรฐาน

บทบาทที่ 1: USER (Personal Account Owner)

สร้างโฟลเดอร์/กระเป๋าบันทึกเงินส่วนตัว (เลือกสีและไอคอนได้), จดบันทึกรายรับ-รายจ่ายผ่านฟอร์มมาตรฐานพร้อมระบุหมวดหมู่และบันทึกช่วยจำ, ยกเลิกรายการหรือย้ายรายการข้ามโฟลเดอร์ด้วยตนเองผ่านระบบ Double-Check, กู้คืนรายการที่ยกเลิกจากถังขยะ, ตั้งงบรายเดือนหรือเลือกใช้สูตรจัดงบแนะนำเพื่อดูยอดที่ใช้ได้ต่อวัน, ตั้งกระปุกออมเงิน และดูรายงานสรุปผล

บทบาทที่ 2: ADMIN (System & Catalog Administrator)

สร้างและจัดการหมวดหมู่มาตรฐานกลางของระบบ (System Categories), สร้างและอัปเดต สูตรจัดงบแนะนำ (Starter Budget Templates) เพื่ออำนวยความสะดวกให้ USER นำไปใช้งาน และช่วยเหลือจัดการปลดล็อกบัญชี/งวดบัญชีเมื่อ USER แจ้งปัญหาเข้ามา โดยไม่มีสิทธิ์เข้าถึงโฟลเดอร์หรือรายการเงินส่วนตัวของ USER

2. Product Scope & Explicit Exclusions

ขอบเขตที่ระบบทำ (In-Scope Baseline)

  • ระบบยืนยันตัวตน (Login/Logout/Current Identity) และแยกสิทธิ์ 2 บทบาท (USER, ADMIN) แบบ Bidirectional RBAC
  • การสร้างโฟลเดอร์บันทึกเงินส่วนตัวหลายใบ (เลือกสี/ไอคอนได้) และการป้องกันการลบโฟลเดอร์ที่มีรายการค้างอยู่แบบ Double-Check
  • การบันทึกรายรับ (INCOME) และรายจ่าย (EXPENSE) ผ่านฟอร์มมาตรฐานพร้อมเกราะป้องกันยอดเงินติดลบ (No Overdraft)
  • ระบบ Double-Check สำหรับยกเลิกรายการ (Cancel), ย้ายรายการข้ามโฟลเดอร์ (Move), และกู้คืนรายการจากถังขยะ (Restore) ด้วยตัวเอง
  • ตัวคำนวณงบใช้ได้รายวัน (Daily Safe-to-Spend), กราฟสัดส่วนรายจ่าย, หมวดหมู่กลาง และสูตรจัดงบแนะนำโดย ADMIN
  • ซองงบประมาณรายหมวดหมู่, โอนเงินข้ามโฟลเดอร์, กระปุกออมเงิน (Sprint 2) และแจ้งเตือนบิลประจำเดือน, CSV Export, ล็อกงวดบัญชี (Sprint 3)

สิ่งที่อยู่นอกขอบเขตชัดเจน (Explicit Exclusions)

  • ไม่ได้ผูกกับบัญชีธนาคารจริง (No Real Bank Integration / Payment Gateway): เป็นเว็บสำหรับให้ผู้ใช้จดบันทึกและคำนวณยอดเงินด้วยตนเอง
  • ไม่ทำระบบสมัครสมาชิกผ่านอีเมลจริง (No Self-Registration / SMTP): ใช้ Reproducible Seeded Accounts ตามข้อกำหนดวิชา
  • ไม่รองรับหลายสกุลเงิน (Single Currency THB): ใช้สกุลเงินบาท (THB) ทศนิยม 2 ตำแหน่ง
  • ไม่รวมปุ่มลัดคีย์ด่วน (No Shortcut Presets), ป้ายอารมณ์ตอนจ่าย, ระบบหารบิลกับเพื่อน หรือเหรียญรางวัลเกม: เพื่อให้หน้าจอสะอาดตาและโฟกัสที่ความถูกต้องทางบัญชีอย่างชัดเจน

4. Business Rules (BR-01 .. BR-08) — อุดช่องโหว่ครบทั้ง 6 จุด

IDBusiness Rule Definition & Validation EnforcementSprint
BR-01 Monetary Precision, Initial Balance & Category Type Match: จำนวนเงินธุรกรรม (amount) ต้อง > 0.00 ทศนิยมไม่เกิน 2 ตำแหน่ง; ยอดเงินตั้งต้นตอนสร้างโฟลเดอร์ (initial_balance) ต้อง >= 0.00; และประเภทธุรกรรม (INCOME | EXPENSE) ต้องตรงกับประเภทของหมวดหมู่ (category.type) เสมอ มิฉะนั้นปฏิเสธด้วย 422 CATEGORY_TYPE_MISMATCH Sprint 1
BR-02 No Folder Overdraft & Atomic Concurrency Rule: ห้ามบันทึกรายจ่าย (EXPENSE) ที่มากกว่า current_balance ของโฟลเดอร์ (ปฏิเสธด้วย 422 INSUFFICIENT_WALLET_BALANCE) และต้องใช้ Atomic Conditional Row Update ใน Database Transaction เพื่อป้องกัน Race Condition จากการยิงตัดเงินพร้อมกัน Sprint 1
BR-03 Bidirectional Role & Strict Personal Privacy Isolation:
• USER เข้าถึงและแก้ไขได้เฉพาะโฟลเดอร์และรายการของตนเองเท่านั้น (ห้ามดูของ USER คนอื่น → 403 FORBIDDEN) และห้ามเรียก API จัดการหมวดหมู่กลางหรือสูตรจัดงบของ ADMIN (403 FORBIDDEN)
• ADMIN ห้ามเปิดดูโฟลเดอร์หรือรายการรายรับ-รายจ่ายส่วนตัวของ USER เด็ดขาด (403 FORBIDDEN) และห้ามสร้าง/ย้าย/ยกเลิกรายการเงินของ USER		 Sprint 1
BR-04 Double-Check Move Transaction Two-Way Balance Sufficiency: การย้ายรายการข้ามโฟลเดอร์ (POST /api/transactions/:id/move) ต้องส่งธงยืนยัน confirmed: true (มิฉะนั้นคืน 400 CONFIRMATION_REQUIRED), โฟลเดอร์ต้นทางและปลายทางต้องเป็นคนละใบกันและเป็นของ USER คนเดียวกัน:
• ถ้าย้ายรายการ EXPENSE จากโฟลเดอร์ A → B: ต้องเช็กว่า B.current_balance >= amount (ถ้าไม่พอคืน 422 INSUFFICIENT_TARGET_BALANCE) แล้วคืนเงินให้ A พร้อมหักเงินจาก B แบบ Atomic
• ถ้าย้ายรายการ INCOME จากโฟลเดอร์ A → B: ต้องเช็กว่า A.current_balance >= amount (ถ้าเงินใน A ถูกใช้ไปจนไม่พอให้ดึงออก คืน 422 INSUFFICIENT_SOURCE_BALANCE) แล้วหักเงินจาก A พร้อมบวกเงินเข้า B แบบ Atomic		 Sprint 1
BR-05 Double-Check Cancel & Trash Restore Balance Integrity:
• การยกเลิกรายการ (POSTED → CANCELED) และการกู้คืนจากถังขยะ (CANCELED → POSTED) ต้องส่ง confirmed: true และห้ามกดซ้ำในสถานะเดิม (409 INVALID_TRANSACTION_STATE)
• ถ้ายกเลิกรายการ INCOME: ยอดคงเหลือปัจจุบันในโฟลเดอร์ต้อง >= amount เพื่อให้หักเงินออกได้โดยไม่ติดลบ (422 INSUFFICIENT_BALANCE_TO_CANCEL)
• ถ้ากู้คืน (Restore) รายการ EXPENSE จากถังขยะ: ยอดคงเหลือปัจจุบันในโฟลเดอร์ต้อง >= amount เพื่อให้หักเงินใหม่ได้โดยไม่ติดลบ (422 INSUFFICIENT_BALANCE_TO_RESTORE)		 Sprint 1
BR-06 Double-Check Folder Archive Protection: โฟลเดอร์ที่มีรายการธุรกรรมอยู่ข้างในห้ามลบออกจากฐานข้อมูลโดยตรง แต่ต้องใช้การเก็บเข้ากรุ (Archive) แบบ Double-Check หรือย้ายรายการออกก่อน เพื่อรักษาความถูกต้องของยอดสรุปรายเดือน Sprint 1
BR-07 Savings Allocation Separation & Distinct Transfer Rule: การโอนเงินข้ามโฟลเดอร์ (F-08) และการหยอดกระปุกออมเงิน (F-09) ต้องไม่ถูกนับรวมเป็นรายจ่ายสิ้นเปลือง (EXPENSE) ในกราฟค่าใช้จ่ายรายเดือน Sprint 2
BR-08 Closed Fiscal Period Immutability: ห้ามเพิ่ม ย้าย ยกเลิก หรือกู้คืนธุรกรรมในเดือนที่ถูกสั่งปิดงวดบัญชี (CLOSED) แล้ว (422 PERIOD_CLOSED) จนกว่าจะได้รับการปลดล็อก Sprint 3
